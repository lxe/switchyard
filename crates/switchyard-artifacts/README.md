# switchyard-artifacts

`switchyard-artifacts` packs filesystem trees into content-addressed, independently zstd-compressed tar chunks, and hydrates those trees through HTTP downloads. It offers complete verification by default and an explicit streaming startup mode for caller-trusted artifacts. It contains no cloud, object-storage, inference-engine, or model-specific configuration.

The blocking `pack(source, out, metadata, options)` function sorts entries, fixes tar ownership and timestamps to zero, preserves ordinary Unix permissions, and hashes files and compressed chunks while streaming. The manifest identity covers the format, metadata, exact entries, and chunk descriptors. `target_shard_bytes` is a soft uncompressed target: a file larger than the target remains intact and is streamed into its own shard.

In the default verified mode, `hydrate(ticket, destination, options, callback)` validates the manifest and bounds total compressed and unpacked bytes before transfer. It rechecks cached chunks, resumes partial responses during retries when HTTP Range is supported, extracts into a private directory next to the destination, verifies the complete tree, and renames the finished directory into place. Download and extraction concurrency have independent limits. A private identity receipt permits an unchanged destination to be reused. An existing directory with another identity or different contents is refused. Complete chunks remain cached when another chunk fails; partial files from a failed call are removed.

Set `HydrationOptions.mode` to `HydrationMode::TrustedStreaming` when the caller already trusts the pinned manifest and its storage/transport. Each HTTP response feeds a zstd/tar decoder immediately, writing disjoint files into private staging while other shards download. No compressed archive cache is written or reread, no manifest identity or file/chunk digest is recomputed, no files or receipt are fsynced, and no complete tree scan follows extraction. Manifest path, link, mode, type, coverage and size rules remain enforced, as do exact HTTP body lengths, decoded bounds, tar metadata and the decompressor's inherent checks. Internal symlinks and final permissions are installed after all writers stop; the complete directory is then renamed into place. This mode accepts structurally valid metadata without proving that its identity matches its contents. HTTPS uses the client's normal TLS validation; plaintext HTTP is also supported for caller-trusted transports and local fixtures.

For twenty simultaneous streaming shards, set both `download_concurrency` and `extraction_concurrency` to 20. The smaller value bounds the combined HTTP/decode workers. Each worker retains one HTTP body part, uses fixed-size file buffers, and limits zstd history to 128 MiB; it never buffers an entire shard. An optional `download_limit: Some(Arc<tokio::sync::Semaphore>)` shares a total HTTP-transfer budget across concurrent hydration calls. Its permits cover each transfer and streaming decoder, including detached workers after cancellation, and are released before retry backoff. A failed streaming attempt removes only its shard's disjoint files and restarts that shard from byte zero; decoded state cannot resume from an arbitrary HTTP Range.

Trusted startup reuses an existing real directory by checking only its matching identity receipt. It does not inspect contents, entry types or extra files inside that directory. The caller must maintain exclusive ownership and decide whether that trust remains appropriate. Trusted reports leave `verified_bytes`, `network_verified_bytes`, `verified_chunks` and `cache_hits` at zero; `downloaded_bytes` remains actual received body bytes, including failed attempts. Progress uses `Extracting` throughout the overlapping transfer/decode phase and never reports `Verifying`. Dropping hydration wakes blocked network readers and cancels writers; staging cleanup waits for the last blocking worker, and workers cannot publish a destination after the async caller disappears.

`verify(destination, manifest)` checks every file digest and size, directory type, symlink target, and entry permission. It rejects extra entries, except the crate's checked `.switchyard-artifact-id` receipt. `Manifest::check_compatibility` compares the caller's required labels with the artifact's metadata; this generic crate does not discover hardware or interpret label names.

Verification performs one topology walk without following symlinks, then hashes every file with bounded parallel workers. The default worker count is the available CPU count capped at eight; `verify_with_options` accepts `VerificationOptions { concurrency }` with a limit from 1 through 64. Each worker reuses a 1 MiB read buffer. In verified mode, both newly extracted staging trees and previously hydrated destinations receive this complete verification.

The `verify` example measures verification without modifying a tree: `cargo run --release -p switchyard-artifacts --example verify -- MANIFEST DIRECTORY [CONCURRENCY]`. On a local i7-13700 running Linux 6.18.54, an already hydrated runtime containing 184,437 entries and 19,345,014,717 file bytes took 12.00 seconds with the previous serial verifier and 1.96 seconds with eight workers, including manifest parsing. These are warm local filesystem measurements, not RunPod cold-start or download measurements. All file hashes, types, permissions, symlink targets, and unexpected entries were checked in both runs.

`Manifest::resolve_entry(path)` validates the manifest and resolves an existing declared path through internal symlinks to its final file or directory entry. Callers can inspect that entry's type and permissions before using it as a program or directory. For example, a mode-0777 symlink to a mode-0644 file resolves to the file's mode 0644. A link to the artifact root returns `None`, because the root has no entry; absent or noncanonical input is rejected.

Paths must be relative UTF-8 paths with canonical slash-separated components. Absolute paths, traversal, special files, privileged permission bits, and symlinks escaping the artifact root are rejected. Symlink targets must name another explicit entry or the artifact root. Link resolution checks intermediate links and parent components using filesystem semantics; cycles and chains exceeding 40 links are refused. Ancestors are inspected without trusting existing symlinks, and archive extraction never uses tar's general-purpose unpack operation. Files must be owner-readable; directories must also be owner-searchable. The artifact root itself is created with mode 0700. Metadata excludes its root directory's original ownership, mode, and timestamps.

File content is processed with fixed-size buffers. Decompression limits each worker's zstd history window to 128 MiB and the decoded stream to the manifest's exact declared length. `request_timeout_s` bounds each complete HTTP attempt, including the body; `stall_timeout_s` separately bounds initial headers and the wait between body chunks. A response that trickles continuously still has to finish within the total deadline.

Progress callbacks may run concurrently on extraction workers and must remain lightweight. `downloaded_bytes` counts response body bytes received, including rejected data and bytes repeated during retries; it excludes HTTP headers and transport framing. `verified_bytes` counts successfully verified compressed chunks, including cache hits. `network_verified_bytes` counts the verified chunks downloaded by this call, without retry duplication. Both verified counters are bounded by the manifest's compressed total. Dropping the hydration future cancels extraction and prevents directory publication; a blocking worker can finish its current bounded operation before noticing cancellation. Signed URLs are neither part of artifact identity nor included in errors or debug output. Artifact metadata is public and must not contain credentials.

Callers must own the source, cache, destination, and their parent directories exclusively while packing, hydrating, or verifying. Filesystem checks reject symlinks present during an operation; they do not establish a security boundary against another process concurrently replacing ancestors. Publication uses a same-filesystem directory rename, without overlays or installation into an existing system tree. Atomic publication guarantees complete visibility, not crash durability of parent-directory metadata. Deterministic byte output requires the same format and zstd implementation version.
